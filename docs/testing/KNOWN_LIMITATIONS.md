# Known limitations

Everything here is a real constraint met during testing or the Test Manager consolidation. Each one says what is affected and what was done instead.

## 1. Test Manager and Kane CLI

| Limitation | Effect | What was done |
|---|---|---|
| Test runs cannot be moved or copied between projects ([TestMu docs](https://www.testmuai.com/support/docs/test-run-bulk-actions/)) | The 7 historical test runs stay in KaneAI Generated | Referenced by run ID, evidence ID, and pack digest in [`EVIDENCE_INDEX.md`](EVIDENCE_INDEX.md); new executions were made in the official project |
| A copied test case carries steps, description, and variables, but not runs or execution history | Destination copies show no runs | The source test case stays the historical record; [`TEST_CASE_MAPPING.md`](TEST_CASE_MAPPING.md) links both |
| A designed test's first run in a folder creates a **new** test case; it cannot be attached to an existing (copied) one | Each retested product test now has two test cases in the destination: the historical copy and the live test case that holds the new run | Both are listed in [`TEST_CASE_INVENTORY.md`](TEST_CASE_INVENTORY.md); the live one is used from now on |
| Test cases whose Kane session never finished stay in *Automation in progress* | They cannot be copied ("Test cases are in automation or could not be copied"), moved ("Remaining test cases are in automation"), or renamed, and they show 0 steps | Source TC-17, TC-18, TC-22, TC-25 stay in KaneAI Generated. Destination TC-37, TC-40, TC-65, TC-85, TC-103, TC-108, TC-115 keep their generated titles; TC-108 and TC-115 stay in the Inbox. TC-103, TC-108, and TC-115 belong to attempt-3 probes that NIARVA judged PASS: their evidence is the worker's record and pack digest, not the test case. No supported control to stop such a session was found in Test Manager or Kane CLI |
| Kane CLI 0.10.4 cannot list, copy, move, or rename test cases | Those operations were done in the Test Manager web interface | Recorded in [`MIGRATION_REPORT.md`](MIGRATION_REPORT.md) §2 |
| No per-run project option for `run`, `testmd run`, `testrun run` | The upload target is the machine-wide profile, or the project stored in a test's local recording | Repository guards refuse a mismatched profile or recording (`scripts/lib/kane-project.mjs`) |
| The profile's folder is one value shared by every agent on the machine | Sessions cannot be sent to different folders per agent or per area | New sessions land in `00 — Inbox` and are filed afterwards |
| Test Manager titles are generated by KaneAI after upload; `--name` only names the local session | New sessions may get generic titles such as `Web || <user> || TC-n` | Renamed afterwards, title only, with a version-history message |

## 3. Kane CLI behavior (from the M0 lab)

| Limitation | Effect |
|---|---|
| `--timeout <s>` does not stop a run | Every runner uses an external process-tree watchdog |
| Runs killed before `run_end` report no credits | About 136 credits in M0 are unaccounted |
| Secret variables are masked in the stream but present inside the sealed evidence pack | Packs stay private; committed records carry digests only |
| Window widths below 800 px cannot be set (`config set-window` rejects them; a CDP Chrome at 390 px still reported 1920 px) | Responsive behavior below 800 px is **not proven by Kane**; such checks are reviewed manually and labelled as manual |
| Transient sign-in failures (`TMS did not return an org_id`, `Token refresh failed`, `Could not resolve credentials`) | The run never starts; it is recorded as UNKNOWN and retried once after a pause |
| Kane does not retain a request that has already completed, and makes a direct HTTP call only for an explicit `Call POST <url> with body …` step that never carries the browser login (found 18 Nov in Assurance tests t-1, t-7, t-8, t-10, t-20, t-32, t-33; t-23 has the same dependency and has not been run) | Steps that inspect a raw request body or call an authenticated API end inconclusive and are recorded as FAIL. The same behavior is covered by server contract probe P-08 and native integration tests, which are reported separately and never counted as Kane proof |
| Replaying a recording from an earlier run can fail on a stale start URL or a changed page state (t-33, 18 Nov) | Recorded as FAIL; the test is rerun so that Kane authors every step against the current build |
| Kane's own `passed` status does not mean the oracle was met | NIARVA computes verdicts from observations; three M0 seeded mismatches were reported `passed` by Kane |

## 4. Coverage not yet proven

The repository holds 64 Kane Assurance-designed tests. As of 18 November 2026, 16:30 WIB, the repository's records show real Kane executions for 26 of them. By latest recorded run: **13 PASS, 13 FAIL, 38 NOT RUN** (per-test list: [`KANE_EXECUTION_REPORT.md` §5](KANE_EXECUTION_REPORT.md#5-latest-status-per-designed-test)). Most FAILs are inconclusive runs in which Kane could not make or observe the request a step needs (§3, last rows); they still count as FAIL. No coverage is claimed for a NOT RUN test. In particular, no designed test has run yet for AI intake and provider outage (t-25 to t-30, t-61), owner response views (t-49 to t-53), or scoped judge access (t-55, t-62 to t-64); NIARVA's own behavior in those areas is covered only by native tests where they exist.

## 5. Process

- The Test Manager web interface was operated through a browser to copy and rename test cases, because Kane CLI has no such commands. That browser was never used to test NIARVA; all NIARVA behavior was observed by Kane CLI.
- Concurrent work by three agents on one machine is serialized by `~/.niarva/kane-run.lock`. A run that waited for the lock is not affected; a run that overlapped another run before the lock existed is recorded as UNKNOWN if it failed for infrastructure reasons.

## 6. Production deployment (Vercel, 18 November 2026)

Details and evidence: [`evidence/deploy/VERCEL-PROD-01.md`](../../evidence/deploy/VERCEL-PROD-01.md).

| Limitation | Effect | What was done |
|---|---|---|
| The worker, Kane CLI, and Chrome cannot run inside Vercel functions | A verification on `https://niarva.vercel.app` progresses only while the owner's worker machine runs `pnpm worker:vercel` | Documented in the README and the deployment guide; a queued run waits and resumes when the worker is back |
| The Neon database is connected to the Production environment only | Preview deployments have no `DATABASE_URL`, so their build stops at the migration step | Deliberate: a feature-branch build must never migrate production data |
| Deployment Protection (Standard) | Only `niarva.vercel.app` is public; deployment-specific URLs ask for a Vercel sign-in | Judges and Kane use the production domain |
| Cold start | The first request after idle took about 12 s (function start and first Neon connection); later requests about 0.4 s | Not tuned |
| Kane CLI loads **every** JSON file in `.testmuai/variables/` | A second file there overrides values of the first (a backup with `start_url=http://localhost:3000` sent five production smoke runs to localhost) | Those runs are recorded as BLOCKED; keep exactly one variables file in that folder |
| Synthetic fixtures live in the production database | Accounts `kane-owner`, `kane-nonowner`, `kane-empty-owner` (`@niarva.test`) and their forms are visible to those accounts only | Synthetic data only; no real personal data |
| A scoped judge account and the demo mode are not configured on the deployment (`DEMO_MODE=false`) | Judge-access tests (t-55, t-62) remain owed | Listed with task C-02 |
